# 5. 前台收银 POS

将现有 Operations 中的 Walk-in 作为基础，新增一套真正用于美容院前台的 POS。POS 必须可以在一张销售单中同时加入多个服务和商品，并完整记录客户、门店、服务员工、折扣、收款、收据、退款和作废。

申请时可将完成后的模块申报为系统自主开发的 in-house POS；现有单项 Walk-in 表单不能单独作为完整 POS 演示。

## 5.1 现有代码可复用的部分

- Operations / Walk-in：保留为前台入口，但结账操作迁移到新的 POS 页面。
- `salon_customers`：用于搜索、选择或新增客户。
- `studio_services`：作为可销售的美容服务目录。
- `shop_products`：作为可销售的零售商品目录，并继续使用现有库存能力。
- `locations`：作为每张销售单的所属门店。
- `payments`：继续作为实际收款、付款状态和退款的财务记录。
- `packages`、`client_packages` 和 `/api/package/buy`：保留现有 Class Pass 的设置、公开销售和 Paid 后发放流程；POS-01 将 Package 纳入统一 Sale Item，PKG-01 再把余额变化升级为 Ledger。
- 现有 HitPay Checkout、Webhook 和付款同步：继续负责线上付款确认。
- 现有发票编号、PDF 和 Email：复用技术基础，但新增适合多项目 POS 的收据模板。
- 现有退款状态转换和操作日志：扩展为 POS 的整单及单项退款审计。

当前代码需要解决的主要缺口：

- Walk-in 一次只能销售一个 Session、Event 或 Service，不能建立多项目购物车。
- Walk-in 只填写访客资料，不能正式选择已有 Salon 客户档案。
- 服务订单没有可靠记录服务员工和销售门店。
- 选择 HitPay 后，现有流程会立即把 Payment 记为 Paid；POS 中必须等待 HitPay Webhook 或主动核实成功后才能完成收款。
- 现有收据/发票逻辑主要按一个 Payment 对应一个项目生成，不能展示多个服务和商品。
- 现有退款主要是整笔退款，不能选择某个项目或部分金额退款。
- 目前没有折扣原因、审批限制、收银班次和每日现金汇总。

## 5.2 POS 页面和基本流程

新增 `/dashboard/pos`，页面按以下顺序操作：

1. 确认当前门店；有全门店权限的用户必须先选择门店，门店员工自动使用自己的门店。
2. 搜索并选择客户，也可以现场新增客户；无须留资料的顾客可以标记为 Walk-in Customer。
3. 从当前门店可售的 Service、Product 和 Package 中加入购物车。
4. 每个服务项目指定实际提供服务的员工；商品可记录销售员工。
5. 输入数量和允许的折扣，系统实时计算小计、折扣和应付总额。
6. 选择 Cash 或 HitPay 收款。
7. 收款成功后生成正式收据，并允许打印、下载 PDF 或发送给客户。
8. 在销售记录中查看详情，并按权限执行退款或作废。

为了避免前台混乱，第一版 POS 不在购物车中销售现有课程 Session 和 Event；它们继续使用原来的 Booking / Walk-in 流程，也不用于 Salon POS 申请演示。现有 Class Pass Package 可以继续公开销售，并逐步接入同一个 POS Sale/Payment 结算事实。

## 5.3 客户选择

收银员可以按姓名、手机号或 Email 搜索 `salon_customers`：

- 搜索到客户后，销售单保存 `salon_customer_id` 和结账时的姓名、电话快照。
- 搜索不到时，可在 POS 内快速新增客户，最少填写姓名和一种联系方式。
- 新增时按标准化手机号和 Email 提示可能重复客户，但不自动合并。
- Walk-in Customer 可以不建立完整档案，但销售单仍保存当次访客名称或 Walk-in 标识。
- 客户的营销同意不能因为 POS 结账被默认勾选，必须由客户明确选择。
- 收款完成后，该服务和消费记录自动出现在客户档案中。

## 5.4 服务、商品和购物车

一张销售单支持多个项目：

- Service：显示名称、时长、门店价格、服务员工、数量和折扣。
- Product：显示商品名称、SKU、单价、数量、库存和折扣。
- Package：显示套餐名称、权益次数、适用服务/门店、有效期和售价；Paid 后才发放客户权益。
- 只显示当前门店可用且状态正常的服务。
- 商品数量不能超过当前门店可售库存；完成付款时才正式扣减库存。
- 同一个服务由不同员工提供时，拆成两个销售明细，确保佣金归属准确。
- 购物车可以修改数量、员工或删除尚未付款的项目。
- 销售完成后保存商品名、服务名、单价、折扣和员工姓名快照，后续改价或改名不影响历史收据。

预约完成后，可以从 Appointment 页面点击 “Take Payment”，自动把客户、门店、服务、员工和预约编号带入 POS，前台只需核对价格并收款。POS 直接新增的 Walk-in 服务必须由有权限员工确认服务已完成并保存 `fulfilled_at`、确认人和服务记录，但不能伪造一个已经完成的 Appointment。未确认完成的服务即使已付款，也暂不产生佣金。

## 5.5 服务员工和销售归属

- 每个服务项目必须指定一名有效员工，且该员工必须属于销售门店或被授权在该门店工作。
- 商品可选择销售员工；未选择时使用当前收银员作为销售归属。
- 销售单同时记录 `location_id`、`cashier_employee_id` 和创建账号。
- 服务明细记录 `service_employee_id`，供客户历史、员工业绩和佣金使用。
- 第一版每个服务明细只支持一名主要服务员工；多人分佣以后再扩展。
- 员工佣金按折扣后的服务净额计算；退款时按实际退款明细自动冲回佣金。
- 前台不能通过修改页面请求，把订单记到自己无权限访问的门店或员工名下；API 必须重新校验。

## 5.6 折扣规则

POS 支持明细折扣和整单折扣：

- 折扣方式：固定金额或百分比。
- 必填折扣原因，可选填写优惠代码或备注。
- 系统记录折扣前金额、折扣金额和折扣后金额。
- 整单折扣按各项目金额比例分摊到明细，保证退款和佣金计算一致。
- 折扣不能使任何项目或整单金额低于零。
- Owner 可以设置 Frontdesk 和 Manager 的最大折扣权限。
- 超过权限的折扣必须由 Owner 或获授权 Manager 输入确认，不允许前台自行绕过。
- 付款完成后不能直接编辑折扣；如有错误，应作废未付款单或对已付款单退款后重新销售。

第一版不需要复杂会员价、礼品卡或自动促销引擎，先保证折扣金额、原因、审批人和审计记录完整。

## 5.7 Cash 和 HitPay 收款

Cash 流程：

- 输入顾客实付现金。
- 系统显示应找金额。
- 确认后建立 Paid Payment，并锁定销售单。
- 保存收款人、收款时间和所属门店。

HitPay 流程：

- 创建 HitPay Payment Request 后，销售单和 Payment 保持 Pending。
- 显示支付链接或 QR，引导顾客付款。
- 只有收到有效 HitPay Webhook，或服务器向 HitPay 查询确认成功后，才改为 Paid 并生成收据。
- 顾客关闭页面、付款超时或只是在 POS 中选择 HitPay，均不能记为 Paid。
- Webhook 和主动同步必须使用同一个幂等键，重复通知不能重复记账、扣库存或计算佣金。
- Pending 期间不能再次完成同一销售单；可以由有权限人员取消后重新选择付款方式。

第一版每张销售单只使用一种付款方式，即 Cash 或 HitPay；暂不做现金加 HitPay 的拆分付款，以控制开发和过审风险。

## 5.8 收据

收款成功后分配唯一且连续可追踪的 POS Receipt Number，生成多项目收据。收据至少显示：

- 商户名称和门店名称
- 收据编号、日期和时间
- 客户姓名或 Walk-in Customer
- 收银员
- 每个服务或商品的名称、数量、单价和服务员工
- 明细折扣、整单折扣和折扣原因
- 小计、税项（如适用）和实收总额
- Cash 或 HitPay 付款方式及交易参考号
- 已退款金额和当前销售状态

复用现有 PDF、Email 和编号基础，但建立新的 POS 多明细模板，不直接使用目前只适合单项目的 Invoice 内容。系统的 GST 注册状态和价格是否含税由商户设置；未启用时不得虚构 GST。

## 5.9 作废和退款

必须清楚区分 Void 和 Refund：

- Void：只用于 Draft、Pending 或尚未完成收款的销售单。必须填写原因，保留原记录，不物理删除。
- Refund：用于已经 Paid 的销售单，支持整单退款、指定项目退款和部分数量/金额退款。
- Cash Refund 记录实际退现金额、执行人、时间和原因。
- HitPay Refund 必须由服务器调用 HitPay 退款，并在服务商确认成功后才更新为 Refunded 或 Partially Refunded。
- 退款金额不能超过该项目和整单尚未退款的金额。
- 商品退款按设置决定是否回补可售库存，并保存操作人和原因。
- 服务退款自动冲回对应员工佣金，但不会删除原预约或客户服务历史。
- 退款后生成 Refund Receipt / Credit Note，并在原收据显示累计退款和净收款。
- 所有作废、退款、审批和状态变化写入不可跳过的审计记录。

现有整笔退款方法可以保留给旧 Payment；POS 需要新增按销售明细退款的数据库事务，不能只把 Payment 状态改成 Refunded。

## 5.10 数据结构建议

新增以下主要数据表：

- `pos_sales`：销售单主表，保存门店、客户、收银员、小计、折扣、税额、总额、已退款金额、状态和收据编号。
- `pos_sale_items`：销售明细，保存 Service / Product / Package 类型、来源 ID、名称和价格快照、数量、分摊折扣、员工、预约及退款数量/金额。
- `pos_payment_allocations`：连接 `pos_sales` 和现有 `payments`，保存每次付款分配金额，第一版仍限制一种付款方式。
- `pos_refunds`：退款主记录，保存退款方式、原因、执行人、HitPay 参考号和状态。
- `pos_refund_items`：记录每个销售明细实际退款的数量和金额。
- `pos_cash_sessions`：记录门店、收银员、开班金额、现金收入、现金退款、预期现金和关班实点金额。
- `pos_discount_approvals`：记录超权限折扣的申请人、审批人、限额和原因。

现有 `payments` 继续作为收款账本，并增加与 POS 销售单的关联。完成付款后，再由系统建立或关联对应的 `service_orders`、商品订单、Package Ledger、库存变动和佣金记录。不要继续用一个 `service_orders`、`client_packages` 或商品订单来冒充整张多项目销售单。

现有 `/api/package/buy` 不删除；它应成为“单一 Package Item 的在线购物车”适配入口，并复用统一 Sale/Payment 结算函数。历史 Package Payment 通过可重跑迁移建立关联或明确标记为 Legacy，不伪造新的付款。

关键金额、商品名、服务名、员工名和门店名必须保存交易快照。所有金额使用数据库 Numeric，并在数据库事务中校验和计算，不能只相信前端传入的总额。

## 5.11 状态和数据库事务

建议销售状态：

- `draft`：正在编辑购物车。
- `pending_payment`：已发起 HitPay，等待确认。
- `paid`：收款完成，可生成正式收据。
- `partially_refunded`：部分退款。
- `refunded`：已全额退款。
- `voided`：未付款前作废。

建立以下服务器端事务：

- `create_pos_sale`：重新读取服务/商品价格和库存，验证门店、员工、折扣权限，并建立 Draft 销售单及明细。
- `complete_pos_cash_sale`：锁定销售单，记录现金付款、扣库存、建立服务记录和佣金、分配收据编号。
- `start_pos_hitpay_payment`：锁定应付金额并建立 Pending Payment Request。
- `complete_pos_hitpay_sale`：仅在服务端核实成功后完成付款、库存、服务记录、佣金和收据。
- `refund_pos_sale_items`：原子校验可退金额，记录退款、回补库存、冲回佣金并更新销售状态。
- `void_pos_sale`：只作废未付款销售单并保留审计。

所有完成付款和退款操作都要支持幂等，任何一步失败时整笔数据库操作回滚，避免出现“已收款但没有订单”或“库存扣了两次”。对于 HitPay 已成功但本地事务暂时失败的情况，由现有付款同步任务自动重试修复。

POS-01 写入入口的 `request_hash` 生成必须统一，避免同一个 `idempotency_key` 因字段归一化差异被误判。具体规则、字段白名单和示例见：`docs/salon-psg/17-pos-idempotency-request-hash.md`。

## 5.12 权限和门店隔离

- Owner：查看所有门店 POS，设置折扣权限，执行或批准退款和作废。
- Location-scoped Manager：只查看和管理授权门店，可在限额内批准折扣及退款。
- Frontdesk：在所属门店开单和收款，只能在授权范围内打折；退款和超额折扣需要审批。
- Service Employee / Instructor：默认只能查看与自己有关的销售和佣金，不具备收款或退款权限。

API 必须按当前账号重新验证门店范围和角色，不能仅依赖页面隐藏按钮。退款、作废、手工同步 HitPay、修改现金实点金额和超额折扣都要记录操作前后内容。

## 5.13 每日收款汇总

新增 `/dashboard/pos/day-close`，按日期、门店和收银员查看：

- 销售单数量
- 服务销售额和商品销售额
- 原价金额、折扣、退款和净销售额
- Cash 收款、Cash 退款和预期现金
- HitPay 收款、HitPay 退款和净额
- 开班现金、关班实点现金和现金差异
- 作废销售单数量及原因

全门店用户可以查看单店或全部门店汇总；门店员工只能查看自己的门店。每日汇总必须来自实际 Paid / Refunded 交易，不能由前台手工输入销售总额。

## 5.14 页面和接口范围

第一版新增：

- `/dashboard/pos`：开单、客户选择、购物车和收款。
- `/dashboard/pos/history`：按日期、门店、客户、员工、付款方式和状态搜索销售。
- `/dashboard/pos/[saleId]`：销售详情、收据、退款和审计记录。
- `/dashboard/pos/day-close`：每日收款及现金关班。
- `/api/pos/sales`：建立和读取销售单。
- `/api/pos/payments/cash`：完成现金付款。
- `/api/pos/payments/hitpay`：发起 HitPay 付款。
- `/api/pos/refunds`：执行整单或明细退款。
- `/api/pos/void`：作废未付款销售单。

第一版暂不做拆分付款、小费、礼品卡、条码扫描、离线收银和钱箱硬件集成。这些不是本次 Salon PSG 过审的核心，避免扩大范围影响交付稳定性。

## 5.15 测试和过审验收

提交前至少验证：

- 可以选择已有客户、快速新增客户或使用 Walk-in Customer。
- 一张销售单可以同时加入多个服务和商品。
- 每个服务都保存实际服务员工，整单保存门店和收银员。
- 无权员工不能跨门店开单、查看销售或指定其他门店员工。
- 普通折扣和超额折扣审批均正确，付款后不能直接改价。
- Cash 正确计算找零，并在付款成功后生成收据。
- HitPay 在 Webhook 或主动核实前始终是 Pending，重复通知不会重复入账。
- 收据完整显示多项目、员工、折扣、付款方式和门店。
- 商品付款成功后扣库存，失败或 Pending 时不扣库存。
- 可以整单退款、单项退款和部分退款，且不能超额退款。
- 商品退款按规则回补库存，服务退款正确冲回员工佣金。
- Void、Refund 和折扣审批均保留原因、操作人和审计记录。
- 每日收款汇总与销售记录、Payment 及退款金额一致。
- 并发点击付款、重复 Webhook 和网络重试不会产生重复 Payment、收据或佣金。

正式技术演示流程：选择门店 → 选择或新增客户 → 加入两个服务、一个商品和一个套餐 → 分别指定服务员工 → 设置一项折扣 → 使用 Cash 完成一单并打印收据 → 使用 HitPay 完成另一单并展示 Pending 到 Paid、套餐权益发放的变化 → 对商品和未使用套餐权益执行受控退款 → 查看库存、Package Ledger、员工佣金、客户服务历史和每日门店汇总同步更新。
